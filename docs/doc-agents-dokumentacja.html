Pojęcia, które warto znać przed lekturą kodu

Węzeł
Zwykła funkcja (state, runtime) -> dict zarejestrowana w grafie. Zwraca tylko te pola stanu, które zmienia.
Stan (DocState)
Dane przebiegu przekazywane między węzłami: mapa projektu, plan, notatki, dokument, recenzja. Słownik typowany (TypedDict), chudy: bez treści plików.
Kontekst (RunContext)
Narzędzia wspólne dla wszystkich węzłów, tworzone raz: config, modele agentów, zapis wyników, spis bazy wiedzy. Węzeł dostaje go przez runtime.context.
Send
Mechanizm LangGraph do równoległego uruchomienia jednego węzła wiele razy. Tu: jeden analityk na każdą jednostkę kodu.
Reducer
Reguła łączenia wyników równoległych węzłów. Pole notes ma operator.add, więc notatki analityków są doklejane, a nie nadpisywane.
Structured output
Model odpowiada obiektem zgodnym ze schematem Pydantic (np. Plan), a nie wolnym tekstem. Wywołanie zawsze przez llm.invoke_structured().
Jednostka kodu
Zadanie dla jednego analityka. W Pythonie jeden niepusty plik źródłowy spoza frameworku.
Szkielet (outline)
Struktura pliku bez pełnej treści: klasy, funkcje, sygnatury, pierwsze akapity docstringów. Buduje go technologia.
Technologia
Wtyczka obsługi języka lub platformy (Python, UiPath). Rdzeń nie zna żadnego języka, pyta tylko technologię.
Baza wiedzy
Pliki Markdown z wiedzą zespołu (frameworki, konwencje, zasady pisania). Planista wybiera z nich te, które przydadzą się dla danego projektu.
Szablony
Pola części formalnej i stałe rozdziały części opisowej w YAML oraz układ dokumentu w Jinja2. Zmiana dokumentu bez zmiany kodu.

  2. Pomocnik do project.json i detect()Rozpoznanie musi być pewne, bo rejestr sprawdza UiPath przed Pythonem. Usuń stałe return False. 
    import json
from xml.etree import ElementTree


def read_project_json(root: str) -> dict:
    """Wczytuje project.json z katalogu projektu; pusty słownik, gdy pliku nie da się odczytać.

    Po co: z project.json korzystają detect(), find_entrypoints() i imports() - jedno miejsce odczytu.
    """
    sciezka = os.path.join(root, "project.json")
    try:
        with open(sciezka, encoding="utf-8-sig", errors="replace") as f:
            dane_projektu = json.load(f)
    except (OSError, ValueError):
        dane_projektu = {}
    return dane_projektu


# --- w klasie UiPathTechnology ---

    def detect(self, root: str, files: list[str]) -> bool:
        """Uznaje projekt za UiPath, gdy w katalogu głównym jest project.json z kluczami typowymi dla UiPatha.

        Po co: implementacja kontraktu Technology.detect(); sam project.json występuje też w innych technologiach.
        """
        czy_uipath = False
        if "project.json" in files:
            dane_projektu = read_project_json(root)
            czy_uipath = "main" in dane_projektu and "dependencies" in dane_projektu
        return czy_uipath
  3. is_source() i find_entrypoints()Kodem są .xaml i .cs. Pliki pomocnicze Studio nie są kodem. 
        def is_source(self, path: str) -> bool:
        """Traktuje jako kod pliki .xaml (workflowy) i .cs (coded workflows), poza katalogami pomocniczymi Studio.

        Po co: implementacja kontraktu Technology.is_source() - tylko te pliki trafią do analityków.
        """
        katalogi_pomocnicze = (".objects/", ".local/", ".settings/", ".screenshots/")
        czy_kod = path.lower().endswith((".xaml", ".cs")) and not path.startswith(katalogi_pomocnicze)
        return czy_kod

    def find_entrypoints(self, root: str, files: list[str]) -> list[str]:
        """Zwraca plik "main" z project.json, potem pliki z listy "entryPoints"; bez project.json - Main.xaml.

        Po co: implementacja kontraktu Technology.find_entrypoints() - opis procesu zaczyna się od startu.
        """
        dane_projektu = read_project_json(root)
        punkty_wejscia = []
        glowny = dane_projektu.get("main", "").replace("\\", "/")
        if glowny != "":
            punkty_wejscia.append(glowny)
        for wpis in dane_projektu.get("entryPoints", []):
            sciezka = wpis.get("filePath", "").replace("\\", "/")
            if sciezka != "" and sciezka not in punkty_wejscia:
                punkty_wejscia.append(sciezka)
        if not punkty_wejscia and "Main.xaml" in files:
            punkty_wejscia.append("Main.xaml")
        return punkty_wejscia
  4. outline(): szkielet workflowuNajważniejsza metoda dla UiPath, bo surowy XAML jest rozwlekły. Parsuj xml.etree.ElementTree, nazwy tagów bez przestrzeni nazw. Minimalny początek (do rozbudowy o zagnieżdżenie, zmienne, Try Catch, adnotacje, assety Orchestratora według docstringu): 
        def outline(self, root: str, path: str) -> str:
        """Zwraca szkielet workflowu .xaml: argumenty, wywołania innych workflowów i aktywności z DisplayName.

        Po co: implementacja kontraktu Technology.outline() - logika workflowu bez szumu znaczników XAML.
        """
        if not path.lower().endswith(".xaml"):
            return ""
        try:
            drzewo = ElementTree.parse(os.path.join(root, path))
        except ElementTree.ParseError:
            return ""
        linie = []
        for element in drzewo.getroot().iter():
            typ = element.tag.split("}")[-1]          # nazwa tagu bez przestrzeni nazw XML
            nazwa = element.get("DisplayName", "")
            if typ == "Property":                     # argument workflowu (x:Members)
                linie.append(f"argument: {element.get('Name')} ({element.get('Type')})")
            elif typ == "InvokeWorkflowFile":
                linie.append(f"wywołuje: {element.get('WorkflowFileName')}")
            elif nazwa != "":
                linie.append(f"{typ}: {nazwa}")
        szkielet = "\n".join(linie)
        return szkielet

Decyzje do podjęcia przy UiPath

  • Pełny XAML czy szkielet? Analityk wysyła pełną treść każdego pliku poniżej analysis.max_file_size_kb (100 KB). Dla XAML szkielet bywa lepszy niż pełna treść. Zmiana wymaga decyzji w rdzeniu (analyst.build_unit_code()), np. nowej metody w kontrakcie technologii.
  • Jednostka kodu = jeden plik. scanner.build_code_units() tworzy jednostkę z każdego pliku. Grupowanie workflowów w procesy to zmiana w skanerze.

Robot Framework

Kiedy: projekty w Robot Framework (pliki .robot i .resource, słowa kluczowe, często biblioteki RPA Framework). To inny format kodu niż .py, więc potrzebne są oba poziomy: technologia i wiedza.

  1. Technologia: detect, is_source, punkty wejściaProjekty RF mają własne biblioteki słów kluczowych w .py, więc is_source() obejmuje też .py, a szkielety i importy plików .py deleguje do PythonTechnology. Dzięki temu nowy plik nie importuje ast (reguła z AGENTS.md). 
    """Obsługa technologii Robot Framework (podklasa Technology).

Co robi: rozpoznaje projekty z plikami .robot, buduje szkielety sekcji (Tasks, Keywords, Settings)
i importy (Library, Resource, Variables). Pliki .py (biblioteki słów kluczowych) obsługuje PythonTechnology.

Test ręczny: python -m doc_agents.technologies.robotframework <katalog projektu>
"""

import os
import re

from doc_agents.technologies.base import Technology
from doc_agents.technologies.python import PythonTechnology


def robot_sections(root: str, path: str) -> dict[str, list[str]]:
    """Dzieli plik .robot/.resource na sekcje: nazwa sekcji małymi literami -> linie sekcji.

    Po co: punkty wejścia, szkielet i importy korzystają z tego samego podziału pliku.
    """
    sekcje = {}
    biezaca = ""
    with open(os.path.join(root, path), encoding="utf-8-sig", errors="replace") as f:
        for linia in f.read().splitlines():
            if linia.startswith("*"):
                biezaca = linia.strip("* ").lower()     # np. "tasks", "keywords", "settings"
                sekcje[biezaca] = []
            elif biezaca != "":
                sekcje[biezaca].append(linia)
    return sekcje


class RobotFrameworkTechnology(Technology):
    """Projekty Robot Framework (w tym RPA Framework)."""

    name = "robotframework"

    def __init__(self):
        """Tworzy pomocniczą obsługę Pythona dla bibliotek słów kluczowych (.py) w projekcie.

        Po co: szkielety i importy .py buduje istniejąca PythonTechnology - bez duplikowania kodu i bez importu ast.
        """
        self.python = PythonTechnology()

    def detect(self, root: str, files: list[str]) -> bool:
        """Uznaje projekt za Robot Framework, gdy jest w nim choć jeden plik .robot.

        Po co: implementacja kontraktu Technology.detect(); rejestr sprawdza RF przed Pythonem.
        """
        czy_robot = any(path.lower().endswith(".robot") for path in files)
        return czy_robot

    def is_source(self, path: str) -> bool:
        """Traktuje jako kod pliki .robot, .resource i biblioteki słów kluczowych .py.

        Po co: implementacja kontraktu Technology.is_source() - wszystkie te pliki trafią do analityków.
        """
        czy_kod = path.lower().endswith((".robot", ".resource")) or self.python.is_source(path)
        return czy_kod

    def find_entrypoints(self, root: str, files: list[str]) -> list[str]:
        """Zwraca pliki .robot z sekcją Tasks albo Test Cases - to je uruchamia polecenie robot.

        Po co: implementacja kontraktu Technology.find_entrypoints().
        """
        punkty_wejscia = []
        for path in files:
            if path.lower().endswith(".robot"):
                sekcje = robot_sections(root, path)
                if "tasks" in sekcje or "test cases" in sekcje:
                    punkty_wejscia.append(path)
        return punkty_wejscia

Technologia: outline() i imports()Szkielet: lista sekcji, nazwy zadań i słów kluczowych (linie bez wcięcia w sekcjach Tasks, Test Cases, Keywords) z pierwszą linią [Documentation] i [Arguments], w Settings: Library, Resource, Variables, Suite Setup/Teardown. Z sekcji Variables tylko nazwy, nigdy wartości (mogą być sekretami). 
        def imports(self, root: str, path: str) -> dict[str, list[str]]:
        """Zwraca zależności z sekcji Settings: Resource i Variables jako internal, biblioteki standardowe RF
        jako stdlib, pozostałe Library jako external. Dla .py deleguje do PythonTechnology.

        Po co: implementacja kontraktu Technology.imports().
        """
        if self.python.is_source(path):
            return self.python.imports(root, path)
        biblioteki_standardowe = {"BuiltIn", "Collections", "DateTime", "Dialogs", "OperatingSystem",
                                  "Process", "Screenshot", "String", "Telnet", "XML"}
        grupy = {"internal": [], "external": [], "stdlib": []}
        for linia in robot_sections(root, path).get("settings", []):
            czesci = re.split(r"\s{2,}|\t", linia.strip())   # RF oddziela komórki 2+ spacjami lub tabulatorem
            if len(czesci) < 2:
                continue
            rodzaj, nazwa = czesci[0].lower(), czesci[1]
            if rodzaj in ("resource", "variables") or nazwa.endswith(".py"):
                grupa = "internal"
            elif rodzaj == "library" and nazwa in biblioteki_standardowe:
                grupa = "stdlib"
            elif rodzaj == "library":
                grupa = "external"
            else:
                continue
            if nazwa not in grupy[grupa]:
                grupy[grupa].append(nazwa)
        importy_w_grupach = {nazwa_grupy: sorted(moduly) for nazwa_grupy, moduly in grupy.items()}
        return importy_w_grupach

    outline() zbuduj analogicznie na robot_sections(); dla .py: return self.python.outline(root, path). Dodaj manual_test() na wzór python.py.

Przewodnik dewelopera: od ogółu do szczegółów

Jak myśleć o tym kodzie, w jakiej kolejności go czytać, jak testować zmiany i gdzie szukać przyczyny błędu.

Całość w pięciu zdaniach

  • main.py wczytuje config, tworzy RunContext i uruchamia graf z graph.py.
  • Skaner bez AI buduje mapę projektu, korzystając z wtyczki technologii (dziś Python).
  • Planista dzieli pracę, analitycy równolegle opisują po jednej jednostce kodu, redaktor składa dokument z notatek i szablonów.
  • Recenzent łączy braki policzone kodem z oceną modelu. Odrzucony dokument wraca do redaktora, najwyżej max_review_rounds razy.
  • Każdy etap zapisuje swój wynik w output/, a final.md to ostatnia wersja dokumentu.

Zasady architektury, których pilnujemy

Agent = czysta funkcja + cienki węzeł

Logika (create_plan, create_note…) działa bez grafu. Węzeł tylko wyjmuje dane ze stanu, woła funkcję, zapisuje wynik i zwraca zmienione pola.

Stan to dane, kontekst to narzędzia

DocState niesie wyniki etapów (chude: ścieżki i metadane). RunContext niesie config, modele i zapis. Modeli nie wkładamy do stanu.

Rdzeń nie zna technologii

Tylko technologies/python.py importuje ast. Skaner i analityk pytają kontrakt Technology.

Jeden punkt dostępu do modeli

Tylko llm.py importuje langchain_openai. Każde wywołanie przez invoke_structured() (ponowienie, czytelny błąd).

Treść poza kodem

Prompty w prompts/, pola i rozdziały w knowledge_base/templates/, reguły skanu i modele w config.yaml. Konkretnych pól nie wpisujemy w kod.

Bezpieczeństwo danych

Sekrety tylko jako metadane. Dane w promptach w tagach. Nazwy plików od modelu przechodzą przez read_kb_file() i find_code_unit().

Konwencje kodu

  • Każda funkcja ma docstring: pierwszy akapit CO robi, drugi zaczyna się od Po co:. Pierwszy akapit trafia też do szkieletów plików.
  • Logika zwraca wartości, wypisuje tylko print_*(). Plik podzielony sekcjami # --- Nazwa ---.
  • Każdy moduł kończy się manual_test() wołanym w if __name__ == "__main__":. Uruchamiamy przez python -m z katalogu repo.
  • Ścieżki tylko os.path, jako str. Pliki encoding="utf-8", obce dodatkowo errors="replace".
  • Prostota: bez walidatorów Pydantic, Literal, ConfigDict. Wyjątek: Field(description=...) w schematach odpowiedzi modelu.
  • Wynik przed return w zmiennej o opisowej, często polskiej nazwie (aktualizacja_stanu, komunikat_bledu).

Znane ograniczenia

  • Jedna jednostka kodu = jeden plik. Technologie, w których proces składa się z wielu plików, mogą wymagać grupowania w skanerze.
  • Importy dynamiczne (importlib.import_module, __import__) nie są wykrywane.
  • Kod nie sprawdza planu od modelu. Pominięta jednostka po cichu nie trafi do analizy.
  • Recenzent ocenia cały dokument od nowa w każdej rundzie i bywa niewyczerpujący, więc akceptacja może zależeć od przebiegu.
  • Brak wznawiania przerwanego przebiegu, liczenia kosztu i logu w pliku (kroki 35–37 planu).
  • probe_llm rekomenduje pierwszą działającą metodę structured output, a dla długich odpowiedzi pewniejsza bywa json_schema.
  • Test ręczny context, planner i graph czyści output/.
